# 通信协议文档

## 1. 帧格式

通信协议采用结构化的帧格式来保证可靠性并便于解析。帧结构详细说明如下：

| 字段            | 大小       | 描述                                                                      |
| ------------- | -------- | ----------------------------------------------------------------------- |
| **FrameHead** | 2 字节     | 帧头，固定值（如 `0xAA 0x55`），便于识别。                                             |
| **Length**    | 2 字节     | 帧总长度，从 **CommandID** 到 **CheckSum**，不包括 FrameHead 和 FrameTail。采用小端格式存储。 |
| **CommandID** | 1 字节     | 命令标识符，用于区分各种命令或数据类型。                                                    |
| **Seq**       | 1 字节     | 序列号，用于配对请求和响应或进行帧计数。                                                    |
| **Payload**   | 可变（N 字节） | 特定于命令的数据载荷。                                                             |
| **CheckSum**  | 2 字节     | CRC16 校验和，从 **CommandID** 计算到 **Payload** 结尾。                           |
| **FrameTail** | 2 字节     | 帧尾，固定值（如 `0x55 0xAA`），用于帧边界验证。                                          |

## 2. 帧布局

| 字段        | 大小       | 值                                   |
| --------- | -------- | ----------------------------------- |
| FrameHead | 2 字节     | `0xAA 0x55`                         |
| Length    | 2 字节     | 帧总长度（从 CommandID 到 CheckSum）小端格式    |
| CommandID | 1 字节     | 命令标识符                               |
| Seq       | 1 字节     | 序列号                                 |
| Payload   | 可变（N 字节） | 命令特定数据                              |
| CheckSum  | 2 字节     | 从 CommandID 到 Payload 结尾计算的 CRC16 值 |
| FrameTail | 2 字节     | `0x55 0xAA`                         |

**帧结构可视化**：  
`FrameHead (2B) | Length (2B) | CommandID (1B) | Seq (1B) | Payload (N B) | CheckSum (2B) | FrameTail (2B)`  
示例：`0xAA 0x55 0xXX 0xXX 0x?? 0x?? ... 0x?? 0x?? 0x55 0xAA`

## 3. 命令定义

CommandID 用于区分不同的操作类型。采用以下分配规则：

- **PC -> 设备**：0x00 - 0x7F（请求或控制命令）
- **设备 -> PC**：0x80 - 0xFF（响应或主动报告）
- **响应命令 ID**：通常将相应请求命令 ID 的最高位设置为 1（即 Request_ID | 0x80）。

### (1) 状态和参数命令

| CommandID | 方向       | 含义     | 备注                            |
| --------- | -------- | ------ | ----------------------------- |
| 0x10      | PC -> 设备 | 请求设备状态 | Payload 可以为空。用于查询设备当前状态。      |
| 0x90      | 设备 -> PC | 设备状态响应 | Payload 包含设备状态信息（如运行中、空闲、错误）。 |
| 0x11      | PC -> 设备 | 设置设备参数 | Payload 包含参数标识符及其值。           |
| 0x91      | 设备 -> PC | 参数设置响应 | Payload 指示成功或失败。失败时可包含错误代码。   |
| 0x12      | PC -> 设备 | 请求设备参数 | Payload 指定要读取的参数。可以为空以请求所有参数。 |
| 0x92      | 设备 -> PC | 设备参数响应 | Payload 包含请求的参数值。             |

### (2) 控制命令

| CommandID | 方向       | 含义            | 备注                     |
| --------- | -------- | ------------- | ---------------------- |
| 0x20      | PC -> 设备 | 启动数据传输        | 命令设备开始发送数据流（如 ADC 数据）。 |
| 0xA0      | 设备 -> PC | 启动命令响应        | 确认启动命令，指示成功或失败。        |
| 0x21      | PC -> 设备 | 停止数据传输        | 命令设备停止数据流。             |
| 0xA1      | 设备 -> PC | 停止命令响应        | 确认停止命令。                |
| 0x22      | PC -> 设备 | 设备复位          | 请求设备软件复位。              |
| 0xA2      | 设备 -> PC | 复位命令响应        | 确认复位命令。通常在复位发生前发送。     |
| 0x2F      | PC -> 设备 | Ping（探测）      | 用于检查通信链路是否活跃。          |
| 0xAF      | 设备 -> PC | Pong（Ping 响应） | 对 Ping 命令的响应，确认链路活跃。   |

### (3) 数据传输命令

| CommandID | 方向       | 含义      | 备注                                                       |
| --------- | -------- | ------- | -------------------------------------------------------- |
| 0x40      | 设备 -> PC | ADC 数据包 | 设备主动发送 ADC 数据。Payload 将包含一个或多个通道的数据。此命令用于流式传输，不需要 PC 响应。 |
| 0x41      | 设备 -> PC | 其他传感器数据 | 可用于其他类型的数据包，如 IMU、温度等。                                   |

### (4) 日志和调试命令

| CommandID | 方向       | 含义   | 备注                                                          |
| --------- | -------- | ---- | ----------------------------------------------------------- |
| 0xE0      | 设备 -> PC | 日志消息 | 设备发送日志字符串用于调试或状态更新。Payload 可包含日志级别（如 INFO、WARN、ERROR）和消息内容。 |

## 4. 总结

1. **协议帧格式**：
   - 通过固定的帧头/帧尾、长度字段和校验和，可以在连续字节流中可靠地识别数据帧。
2. **指令/命令的 CommandID**：
   - 用于区分不同的请求、响应或数据类型。
   - Seq 字段用于匹配请求-响应或进行帧计数，防止乱序或丢包。
3. **CRC16**：
   - 虽然 USB CDC 或串口可以保证物理层的可靠性，但在应用层添加 CRC16 进一步保证了帧结构的完整性，可以检测逻辑错误（如缓冲区溢出、对齐错误等）。
   - 以下是 C 语言中计算 CRC16 的函数：

```c
#include <stdio.h>
#include <stdint.h>

// 计算 CRC16 的函数
uint16_t CRC16_Calc(const uint8_t* data, uint16_t length, uint16_t initVal)
{
    uint16_t crc = initVal;  // 初始值通常可设置为 0xFFFF、0x0000 等

    for (uint16_t i = 0; i < length; i++) {
        crc ^= (uint16_t)data[i];
        for (uint8_t j = 0; j < 8; j++) {
            if (crc & 0x0001) {
                crc >>= 1;
                crc ^= 0xA001;  // 常用多项式
            }
            else {
                crc >>= 1;
            }
        }
    }
    return crc;
}
```

4. **C 语言示例**：
   - 提供了 buildFrame() 和 parseFrame() 函数，可以直接在 PC 上测试，也可以移植到 MCU + PC 的双端。
5. **扩展**：
   - 在实际项目中，可以定义更多命令字。
   - Payload 部分可以根据需要添加结构体或二进制数据。
   - CRC 算法可以替换为项目中现有的版本。
   - 如果需要支持更大的数据量，可以在应用层实现分段传输或多帧拼接。

# 支持多帧的 I/O 缓冲区实现

为了实现多帧数据的连续发送和接收，需要一个循环队列或 FIFO 来存储原始输入数据和待发送的帧。以下是一个示例实现，包括：

- **Rx Buffer（接收缓冲区）**：用于缓存原始输入字节流，支持通过 feedRxBuffer() 函数放入新字节，并使用 tryParseFramesFromRx() 解析其中的一个或多个帧。
- **Tx Buffer（发送缓冲区）**：按顺序排队构建好的帧，并在发送线程或中断中检索和传输它们。

### 总结：

1. 循环队列的容量可以根据需求增加。RX_BUFFER_SIZE 和 TX_BUFFER_SIZE 需要根据实际通信速率和业务数据量设置。
2. 如果接收端跟不上发送端，可能导致循环队列溢出。在 feedRxBuffer() / enqueueTxFrame() 中检测到空间不足时，可以执行丢包、阻塞等待或其他适当的处理。
3. 在示例中，将多个帧放入 TxBuffer 时，使用 frameLen + frameData 的方法进行分隔；也可以采用"帧头-帧尾"方法将整个帧存储在 TxBuffer 中。关键是在出队时区分每个帧的边界。
4. 对于实际项目，串口发送和接收通常发生在中断或 DMA 回调中。一旦有新数据可用，就将其送入 RxBuffer()。定期在主循环或任务中调用 tryParseFramesFromRx() 函数，每次可能解析多个帧。
5. 同样，发送端也可以在独立任务或定时器中，根据 dequeueTxFrame() 将每个帧发送到硬件外设。
6. 通过这种方法，可以稳定地发送和接收多帧数据，单帧逻辑可以在应用层使用 buildFrame() / parseFrame() 处理，层次清晰，易于扩展。
